# PRD — opti-calc

## 产品目标

- 让不会建模的人也能算清「怎么安排最划算」这类问题，并且**信任**算出来的数字。
- 把一次性的手算过程变成可反复修改的模型：改个数字，答案立刻重算。
- 当问题本身问得不完整时，明确告诉用户缺什么，而不是随手给一个看似合理的答案。

## 用户与使用场景

**目标用户**

普通玩家、小店主、家庭记账者——会遇到带约束的取舍问题，但没有运筹学背景，也不打算学。他们要的不是「建模能力」，而是「一个答案」。

**典型场景**

| 场景         | 用户在问什么                                                               |
| ------------ | -------------------------------------------------------------------------- |
| 游戏资源规划 | 肥料按 10 小时一份卖、不能拆，我还缺 31.9 小时，该买几份？钱不够要等多久？ |
| 收益最大化   | 96 格地、1000 块预算，两种作物占格数和收益不同，怎么种总收益最高？         |
| 成本核算     | 固定成本 12000、单价 45、单位变动成本 21，卖多少件保本？                   |
| 配料 / 配比  | 两种原料营养和价格不同，满足营养下限的前提下怎么配最省钱？                 |
| 反推未知量   | 已知总数和部分构成，求剩下那部分是多少？                                   |

## 核心问题

现有工具在这个场景下都不合适：

- **Excel 规划求解 / 专业建模软件**：能力足够，但要求用户先理解「决策变量、约束、目标函数」这套概念，门槛挡住了目标用户。
- **计算器 / 手算**：门槛低，但一次只能算一个固定算式，改数字要重来；且中间步骤容易引入舍入误差——真实文档里「等待 29.74 分钟」就是先把 11.9÷24 舍成 0.496 再乘 60 的结果，精确值是 29.75。这类偏差在算账场景里会一路传导到最终决策。
- **各类单一场景小工具**：只能算写死的那一种问题，换个场景就没用了。

因此需要的是：**表达力接近专业工具，但门槛接近自然语言；且数值上绝对可信。**

## 功能及其意义

| 功能                         | 解决什么                           | 为什么需要                                                                                            |
| ---------------------------- | ---------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 日常写法的模型语法           | 专业 DSL 的门槛                    | 变量名可以用中文（`普通份数`）、`2x` 可省略乘号、全角符号自动转换——用户按已有习惯写就行，不必学新记法 |
| 自动求解（无需点按钮）       | 操作步骤负担                       | 输入停顿 300ms 后自动重算，改数字即时看到新答案，符合「算账」的试算节奏                               |
| 精确有理数运算               | 浮点误差导致的错误决策             | 「买几份」差一份就是几十块钱；0.1+0.2≠0.3 这类误差在钱和时长上没有容忍度                              |
| 整数 / 二元变量              | 现实中不可分割的量                 | 肥料不能拆开卖、作物不能种半株。若只做连续求解，会给出「3.19 份」这种买不到的答案                     |
| 内置真实算例                 | 冷启动不知道怎么写                 | 用户挑一个接近自己问题的算例改数字即可上手，这是面向一般人群的关键入口                                |
| 语法高亮 + 行号 + 错误行标注 | 不知道哪里写错了                   | 错误直接标在出错行，消息说明原因和下一步，而不是抛一句「语法错误」                                    |
| 无解 / 无界的可操作提示      | 拿到失败结果不知道怎么办           | 「无界」对一般人是术语，需翻译成「还缺一个限制条件，现实中总会有预算或库存上限」                      |
| 解唯一性判定与提示           | 误把「其中一个解」当成「唯一答案」 | 三个未知数只给两个方程时，必须说明「尚缺 1 个条件」，否则用户会以为答案就是它                         |
| 约束核对表                   | 不信任黑箱结果                     | 逐条列出每个约束的余量、是否取等，用户能自己验证答案合理                                              |
| 语法速查                     | 想写新模型时无从下手               | 折叠式，按「最常写错的顺序」排列；靠示例入门的人不必先读文档                                          |
| 本地持久化                   | 刷新丢失工作                       | 模型存 localStorage，不上传——算账内容常含个人财务信息                                                 |
| 非线性结构明确拒绝           | 静默给出错误答案                   | 变量相乘、分式等超出现有算法，必须明确拒绝并说明原因，而不是近似后当精确解给出                        |

## 功能之间的关系

```
用户输入模型文本
      ↓
 语法高亮 + 行号        ← 写作时的即时反馈
      ↓
  自动求解（防抖）
      ↓
 ┌────┴────────────────────────┐
 ↓                             ↓
语法/语义错误                求解成功
 ↓                             ↓
错误行标注 + 原因         ┌────┴────┬──────────┐
（指导下一步）            ↓         ↓          ↓
                     目标值    变量取值   约束核对表
                              + 唯一性提示
                              + 诊断信息
                              （无解/无界/解不唯一）
```

两条支撑线贯穿始终：

- **示例库** 是入口——先让用户看到能算什么，再让他改。
- **语法速查** 是进阶——从改示例过渡到写自己的模型。

## 范围与非目标

**范围内**

- 线性模型：多元一次方程组、线性不等式、线性目标最值、整数与二元变量。
- 单机浏览器运行，无需注册、无需联网。
- 中文优先的语法与提示文案。

**范围外**

- **非线性 / 非凸问题**：变量相乘、多项式、分式规划、`!=` 约束。超出当前算法能力，明确拒绝而非近似。
- **服务端能力**：账号、云同步、协作编辑、模型分享。需要时应升级为全栈架构，不在纯前端上硬叠。
- **大规模优化性能**：目标是「日常算账」规模（几十个变量），不追求工业级 MILP 求解速度。
- **SEO 与预渲染**：客户端渲染 SPA。
- **移动端深度适配**：当前布局在窄屏可用但未专门优化。
