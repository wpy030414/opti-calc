## ADR-001：自研求解内核，不引入第三方数学库

- **日期**：2026-10-19
- **状态**：已采纳
- **背景**：需要求解多元线性方程组、线性规划与整数规划。现成选择有 `mathjs`（表达式求值）、`javascript-lp-solver`（LP/MILP）、`numeric.js`（矩阵）等。
- **考虑过的方案**：
  1. 组合现成库：`mathjs` 解析 + `javascript-lp-solver` 求解
  2. 完全自研内核
- **决策**：完全自研（`src/solver/`，约 2900 行）。
- **为什么选这个**：
  - 现成 LP 库全部基于 IEEE 754 浮点，`0.1 + 0.2 ≠ 0.3`。算账场景里这会直接导致「买 3 份」算成「买 4 份」，而这是产品要解决的核心痛点，不是边角问题。
  - 现成库的输入是 JSON 结构（`{constraints, variables, ints}`），用户仍需在「自然语言」与「JSON」之间做一次心智转换——门槛没降下来。自研 DSL 才能让变量名用中文、让 `2x` 省略乘号。
  - 需要区分「无解 / 无界 / 解不唯一 / 尚缺几个条件」，这是诊断能力而非求解能力，现成库只返回一个状态码。
- **为什么不选其他**：方案 1 能省下约 2000 行代码，但浮点误差与输入门槛这两个核心问题都解决不了。
- **后果**：
  - 需自行保证算法正确性，因此测试投入显著（123 个测试，其中 `tests/e2e/qq-farm.test.ts` 用真实算账文档逐条验收）。
  - bundle 405 KB（gzip 132 KB），其中求解内核约 2900 行占比不大，主要是 React。
  - 性能上限低于成熟求解器（无割平面、无预处理、无对偶单纯形）。
- **何时重新审视**：当用户提出需要非线性模型、或变量规模超过数千时。届时应评估引入 WASM 编译的成熟求解器（如 HiGHS），而不是继续加强自研内核。

## ADR-002：全程 BigInt 精确有理数，禁用浮点

- **日期**：2026-10-19
- **状态**：已采纳
- **背景**：ADR-001 确定自研后，数值表示是第一个必须定的地基。
- **考虑过的方案**：
  1. `number` + 容差比较（`Math.abs(a-b) < 1e-9`）
  2. 定点数（放大 10^k 后用 BigInt 整数）
  3. 有理数 `p/q`（BigInt 分子分母，随时约分）
- **决策**：方案 3，实现为 `src/solver/frac.ts` 的 `Frac` 类。不变量：`d > 0`、`gcd(|n|, d) === 1`、零统一为 `0/1`。
- **为什么选这个**：
  - 线性代数的中间结果天然是分数（`11.9/24 = 119/240`）。方案 3 下这些值全程精确，无需选择容差。
  - 容差比较会污染所有判据：单纯形的「检验数是否 ≥ 0」、最小比值检验、RREF 的「该行是否全零」、整数判定的「是否恰好是整数」。每一处都要选一个 epsilon，而任何固定 epsilon 都有反例。
  - 定点数（方案 2）在除法时会丢精度或需要动态调整小数位，本质上退化成方案 3 的一个受限版本。
- **为什么不选其他**：方案 1 是最省事的做法，但它把「精度」变成一个需要全程调试的隐式参数。用户看不到 epsilon，却会看到「等 29.74 分钟」这种因舍入而错的答案。
- **后果**：
  - `Frac.parse('0.1')` 走字符串解析而非 `Number(v)`，因此 `0.1` 精确等于 `1/10`。
  - BigInt 位数会随消元膨胀。缓解措施：高斯消元选主元时优先取绝对值最小的非零元；`mul` 里做交叉约分。
  - `toNumber()` 存在但仅限展示层使用。任何 `parseFloat` / `Number()` 出现在求解链路里都视为缺陷。
- **何时重新审视**：若出现位数爆炸导致明显卡顿（当前规模下未观察到），可考虑对小数值走浮点快速路径、仅在判据处回到精确算术。

## ADR-003：两阶段单纯形 + Bland 规则，而非 Big-M

- **日期**：2026-10-19
- **状态**：已采纳
- **背景**：`lp.ts` 需要一个能找到初始可行基的方法。
- **考虑过的方案**：
  1. Big-M：给人工变量一个极大惩罚系数 M，单阶段求解
  2. 两阶段法：第一阶段最小化人工变量之和，第二阶段求原目标
  3. 对偶单纯形
- **决策**：方案 2，配 Bland 规则（进基取最小下标的负检验数；出基在比值并列时取基变量下标最小者）。
- **为什么选这个**：
  - Big-M 与精确算术根本冲突。M 无论取多大都是有限值，「人工变量是否真的被赶出基」的判据会被 M 污染；取无穷大则无法参与 BigInt 运算。两阶段法没有这个妥协——第一阶段目标值 > 0 即严格不可行。
  - Bland 规则可证明不会循环，因此不需要退化扰动这类启发式补丁。启发式在精确算术下反而危险：扰动会破坏「精确」这个前提。
  - 主元优先选绝对值最小的非零元，抑制 BigInt 位数膨胀。
- **为什么不选其他**：方案 1 在浮点实现里是常见做法，但在 ADR-002 的前提下站不住。方案 3 适合「已有对偶可行基」的场景（如参数化规划），本项目用不上。
- **后果**：
  - 需要维护「把仍在基中的人工变量换出」这一步；冗余约束行（整行全零）标记为 `basis[i] = -1`。
  - 迭代次数上限 `400 × (m + n + 1)`，超出报 `degenerate` 而非挂死。
  - 变量数较多时比 Big-M 多一次完整求解。日常算账规模下开销可忽略。
- **何时重新审视**：若需要支持参数化规划或灵敏度分析，应补充对偶单纯形。

## ADR-004：高斯消元降级为「诊断」，出解统一走 MILP

- **日期**：2026-10-19
- **状态**：已采纳
- **背景**：无目标函数的模型（「求定点」）最初实现为：等式用高斯消元解出，再检查该解是否满足不等式与整数约束。结果暴露一个语义缺陷——等式系统有唯一实数解 `x = 7.5`、但用户声明 `x : 整数` 时，直接判 infeasible 是错的：放宽某条等式后其实存在整数解。两套可行性判定逻辑（消元的 + 手工检查的）会互相漂移。
- **考虑过的方案**：
  1. 高斯消元出解 + 手工校验不等式与边界
  2. 高斯消元只做诊断，实际解统一由 MILP 给出
- **决策**：方案 2。`solve.ts` 里高斯消元只用于两件事：(a) 等式自相矛盾时立即报 infeasible 并指出矛盾行；(b) 用 `describeRank` 告诉用户「尚缺几个条件」。
- **为什么选这个**：等式、不等式、变量边界、整数约束全部走同一条路径，可行性判定只有一处实现。高斯消元保留了它真正不可替代的能力——区分唯一 / 无穷多 / 矛盾并给出解空间维度，这是 LP 做不到的（LP 只返回一个顶点，无法告诉用户「其实还差一个条件」）。
- **为什么不选其他**：方案 1 代码更短，但「无目标 + 整数约束 + 不等式」这个组合下会给出错误结论，而这个组合恰恰是算账场景的常态。
- **后果**：
  - 无目标路径要跑一次零目标 MILP，比单纯消元慢。
  - `enrichInfeasibleReason` 会在报无解时补充「等式部分本身有唯一解 X，但它违反了不等式 / 边界 / 整数约束」，否则用户只看到「无可行解」无从下手。
  - 唯一性探测有两个方向，必须区分：无目标时在**整个可行域**上逐变量求 max/min；有目标时必须先把「目标值 = 最优值」锁成等式，在该**切面**上探测，否则变量只要能动就会误报「最优解不唯一」。
- **何时重新审视**：若诊断成为性能瓶颈（当前不是），可考虑先消元再对缩减后的系统跑 MILP。

## ADR-005：`vite.config.ts` 用 `lazyPlugins(() => react())`

- **日期**：2026-10-19
- **状态**：已采纳
- **背景**：写成常规形式 `plugins: [react()]` 后，`tsc --noEmit` 直接崩溃：
  ```
  Error: Debug Failure. False expression: parameter should have errors when reporting errors
      at getSignatureApplicabilityError
      at checkExportAssignment
  ```
  这不是类型错误，是 TypeScript 内部断言失败。
- **考虑过的方案**：
  1. 把 `vite.config.ts` 从 tsconfig 的 `include` 里排除，不做类型检查
  2. `plugins: [...react()]`（展开成扁平数组）
  3. `plugins: lazyPlugins(() => react())`
- **决策**：方案 3。
- **为什么选这个**：
  - 根因是两套**名义不同但结构相同**的巨型类型相撞：`@vitejs/plugin-react` 的类型来自真实 `vite@8.3.4`，而 vp 的 `defineConfig` 用的是别名包 `@voidzero-dev/vite-plus-core` 的 `Plugin`。TS 在 `defineConfig` 的多重载上比较这两个类型时触发内部断言失败。
  - `lazyPlugins` 是 vp 官方导出、专门包装插件的 API，签名 `lazyPlugins(cb: () => PluginOption[])`，因此类型落在 vp 自己的类型体系内，不触发跨包比较。
  - 它有真实的运行时价值：vp 在只读配置元数据的场景（`vp fmt` / `vp lint`）会跳过插件工厂，避免为了跑个格式化就加载整条 React 插件链。
- **为什么不选其他**：方案 1 会让配置文件失去类型保护——`base`、`fmt`、`lint`、`test` 这些字段写错了没人发现。方案 2 实测仍崩溃，因为问题在类型比较而非数组嵌套层级。
- **后果**：
  - 参数必须是回调 `() => react()`。直接传 `react` 只是碰巧签名兼容，语义是错的。
  - 若将来 vp 修复了这个类型问题，可以改回常规写法，但 `lazyPlugins` 的懒加载收益仍然值得保留。
- **何时重新审视**：vp 升级后如果 `[react()]` 不再崩溃，可评估是否简化；否则保持现状。

## ADR-006：未声明的变量默认自由（可取负值）

- **日期**：2026-10-19
- **状态**：已采纳
- **背景**：LP 标准形要求变量 ≥ 0，多数建模语言的默认约定也是非负。但本产品的目标用户是算账的人。
- **考虑过的方案**：
  1. 默认非负（`x >= 0`），需要负值时显式声明
  2. 默认自由，需要非负时显式声明「非负」/「非负整数」
- **决策**：方案 2。类型别名表里 `非负` / `非负整数` / `正整数` / `自然数` / `二元` 自带隐式下界；裸 `实数` / `整数` 或完全未声明则无下界。另有 `free` / `自由` 修饰符显式表达意图。
- **为什么选这个**：算账里负数是有意义的一等公民——亏损、欠款、盈亏差额。若默认非负，用户写 `盈亏 = 收入 - 成本` 后会得到「无解」，而错误原因（默认下界）离他的直觉太远。让默认符合领域直觉，比让默认符合算法惯例更重要。
- **为什么不选其他**：方案 1 是运筹学惯例，但它的合理性建立在「用户已经理解标准形」的前提上，而本产品的前提恰恰相反。
- **后果**：
  - 自由变量在标准化时拆分为 `x = x⁺ - x⁻`，矩阵列数增加。
  - 目标无界的概率上升（少了默认下界的约束），因此「无界」提示文案必须给出可操作的下一步：「现实中总会有预算、库存或时间上限，把它写成一条 `<=` 约束」。
  - 严格不等式（`<` / `>`）的处理要分类型：整数变量精确收紧（`x < 5` → `x <= 4`），实数变量只能放宽为闭区间并记 warning（开集没有最值）。
- **何时重新审视**：若用户反馈「忘了写非负导致答案出现负数」的频率高于「负数被意外禁止」，说明默认选错了，应重新评估。

## ADR-007：`==` 在词法层归一化为 `=`

- **日期**：2026-10-19
- **状态**：已采纳
- **背景**：用户从编程语言带来的习惯是写 `==`。最初 lexer 原样产出 `==`，`RelOp` 类型里却没有它，parser 用 `cmpTok.value as RelOp` 强转——运行时存在类型系统不知道的值。
- **考虑过的方案**：
  1. `RelOp` 加上 `'=='`，各处判等写成 `op === '=' || op === '=='`
  2. lexer 归一化 `==` → `=`
- **决策**：方案 2。
- **为什么选这个**：语法层只保留一套等号，`RelOp` 类型才不会被 `as` 断言塞进类型里不存在的值。parser 里改用查表 `CMP_TO_RELOP` 而非断言——断言会让任何新增 Token 值静默通过类型检查，查表则把「lexer 产出了 parser 不认识的比较符」变成显式错误。
- **为什么不选其他**：方案 1 让同一个语义有两个字面量，所有 switch 与 filter 都要写两个分支。这类「忘记加 `|| op === '=='`」的 bug 极难发现，因为它只在特定输入下静默给出错误结果。
- **后果**：清理了三处死代码（`solve.ts` 的等式过滤、`standardize.ts` 的 `OP_SENSE`、测试辅助）。`OP_SENSE` 因此可以收紧为 `Record<RelOp, RelSense>`，漏映射会被类型检查抓住。
- **何时重新审视**：无需重新审视，这是纯粹的正确性修复。

## ADR-008：错误位置只存结构化字段，不拼进消息文本

- **日期**：2026-10-19
- **状态**：已采纳
- **背景**：组件渲染测试跑出真实的 UI 缺陷：面板显示「第 1 行：出现意外的「EOF」（第 1 行第 5 列）」——同一个位置信息说了两遍。根因是 `SolverError` 已用 `line` / `col` 字段承载位置，但 lexer / parser / linearize 又把位置拼进了 `message`，UI 再加一次前缀。
- **考虑过的方案**：
  1. UI 不加前缀，直接用消息原文
  2. 消息只承载语义，位置由 `line` / `col` 字段承载，UI 决定如何呈现
- **决策**：方案 2。`SolverError.describe()` 提供「第 N 行：语义」的完整文本给需要一次性拿到的调用方。
- **为什么选这个**：编辑器高亮整行，因此 UI 只需要行号；而命令行调用方可能想要行列号。位置怎么呈现是**调用方的决策**，不该由抛错处固化在字符串里。
- **为什么不选其他**：方案 1 治标不治本——位置信息散落在几十个字符串模板里，将来改呈现方式要改所有抛错处。
- **后果**：
  - 清理了约 20 处消息文本。
  - **例外**：`warnings` 是纯字符串数组，没有结构化字段承载位置，因此警告文本**必须**自带行号，否则用户无从定位。这条例外已在 `errors.ts` 与 `ARCHITECTURE.md` 中写明。
  - 新增回归测试「错误消息不重复显示行号」，断言 `第 1 行：` 存在且 `第 1 行第` 不存在。
- **何时重新审视**：若将来要给 warning 也加结构化位置（如可点击跳转到行），应同步移除 warning 文本里的行号。

## ADR-009：localStorage 惰性写入

- **日期**：2026-10-19
- **状态**：已采纳
- **背景**：`useLocalStorage` 最初在挂载时就把初始值写盘，测试断言「挂载后 localStorage 有值」。
- **考虑过的方案**：
  1. 挂载即写入初始值
  2. 惰性写入：仅在用户实际编辑时落盘
- **决策**：方案 2，并修正测试断言为「挂载后为 `null`，编辑后才有值」。
- **为什么选这个**：若挂载即写盘，日后调整默认算例（`DEFAULT_SOURCE`）会把老用户的存档顶掉——他们上次打开时看到的默认值被写进了 storage，新版本读到旧值，永远看不到新默认。惰性写入让「用户从未编辑过」这个状态可被识别。
- **为什么不选其他**：方案 1 实现上只差一行，但它把一个将来的维护动作变成了数据破坏。
- **后果**：
  - 读取失败（隐私模式 / 配额满 / JSON 损坏）静默回退到初始值，写入失败只忽略，绝不让应用白屏。已有测试覆盖损坏 JSON 的回退。
  - 监听 `storage` 事件做跨标签页同步，多开页面不会互相覆盖成旧值。
- **何时重新审视**：若将来引入「恢复默认」按钮，需要能区分「无存档」与「存档等于默认值」，当前设计已支持（无存档即 `null`）。

## ADR-010：求解同步执行，不引入 Web Worker

- **日期**：2026-10-19
- **状态**：已采纳
- **背景**：求解在渲染路径上执行，需要决定是否放到 Worker 里避免阻塞主线程。
- **考虑过的方案**：
  1. Web Worker + 消息传递
  2. 同步执行 + 300ms 输入防抖
- **决策**：方案 2。
- **为什么选这个**：
  - 求解是精确有理数算术，日常算账规模（几十个变量）耗时在毫秒级，123 个测试整套跑完 8.45 秒，其中组件测试因 jsdom 与防抖等待占绝大部分，单次求解远低于此。
  - Worker 会把 `Frac` 这类含 BigInt 的对象卷入结构化克隆，错误处理与类型共享都要额外做一层，复杂度上升而收益为零。
  - 防抖解决的是真实问题（逐字符重算导致面板闪烁），而 Worker 解决的是一个不存在的问题（求解太慢）。
- **为什么不选其他**：方案 1 在模型规模大到秒级求解时才有意义。
- **后果**：迁移成本被刻意压低——求解入口只有 `solve(source)` 一个纯函数，内核不含任何 DOM 依赖，将来换成 Worker 只需改 `App.tsx` 里那一个 `useMemo`。
- **何时重新审视**：当出现「变量数上百的整数规划」这类需求、或用户反馈输入卡顿时。届时先量测单次求解耗时，确认是求解而非渲染慢，再上 Worker。

## ADR-011：按行分句解析，而非整体递归下降

- **日期**：2026-10-19
- **状态**：已采纳
- **背景**：模型文本是多条独立语句。需要决定 parser 的结构。
- **考虑过的方案**：
  1. 把整份文本当一个 Token 流，用分隔符规则切分语句
  2. 先按行切分，每行独立解析为一条语句
- **决策**：方案 2。`parse()` 逐行 `tokenize` + `LineParser`，行号即真实行号。
- **为什么选这个**：
  - 错误定位天然精确——出错 Token 的行号就是物理行号，编辑器可以直接高亮该行。方案 1 需要额外维护「Token 偏移 → 行列」的映射，且跨行歧义（`x = 1\n-2` 是一条还是两条？）会不断产生边界情况。
  - 与产品语法契合：本语法**规定**一行一条语句，不存在跨行表达式。按行分句不是妥协，是语法本身的形状。
  - 语法高亮也因此可以按行独立着色，不需要跨行状态机，不会出现「前面写错导致后面全乱」的连锁失准。
- **为什么不选其他**：方案 1 更通用，但通用性用不上，而代价（位置映射、跨行歧义）是实打实的。
- **后果**：
  - 不支持跨行表达式。若将来要支持，需要引入续行符或括号内换行规则。
  - `stripLineComment` 与 `commentStart` 被导出给 `ModelEditor` 复用，确保高亮与解析共用同一份注释规则。
- **何时重新审视**：若用户反馈长表达式写不下需要换行。

## ADR-012：组件测试从 `vite-plus/test` 导入，不用 `vitest`

- **日期**：2026-10-19
- **状态**：已采纳
- **背景**：`vp test` 能正常运行测试，但 `tsc --noEmit` 报 `Cannot find module 'vitest'`。
- **考虑过的方案**：
  1. `pnpm add -D vitest` 显式安装
  2. 从 `vite-plus/test` 导入
- **决策**：方案 2。
- **为什么选这个**：vitest 5.0.5 是 `vite-plus` 的依赖，pnpm 的严格隔离让它存在于 `.pnpm` store 但没有提升到顶层 `node_modules`，因此 `tsc` 找不到类型。`vite-plus/test` 的内容就是 `export * from 'vitest'`，是官方提供的转发出口，类型与运行时都能正确解析。已用探针文件验证过两者均可用。
- **为什么不选其他**：方案 1 会让项目里出现两个 vitest 版本来源（vp 内置的 5.0.5 与自己装的），版本漂移时行为难以预测。这与 node-page 路线「不在 package.json 写 packageManager、统一由 vp 代理」的约定精神一致。
- **后果**：
  - 组件测试文件首行需要 `// @vitest-environment jsdom` docblock，因为 `vite.config.ts` 里 `test.environment` 默认是 `node`。
  - `test.include` 扩展到 `.tsx` 以纳入组件测试。
  - jsdom 需要显式安装（vp 未内置）。
- **何时重新审视**：若 vp 将来把 vitest 提升为直接依赖，可改回 `vitest` 导入；但当前写法在两种情况下都能工作，无需改动。

## ADR-013：分支定界用深度优先，不用最优优先

- **日期**：2026-10-19
- **状态**：已采纳
- **背景**：`milp.ts` 需要选择搜索策略。
- **考虑过的方案**：
  1. 最优优先（best-first）：用优先队列按 LP 松弛值排序
  2. 深度优先（DFS）：栈 + 界剪枝
- **决策**：方案 2。
- **为什么选这个**：
  - 深度优先能尽早拿到一个可行整数解，从而收紧上界、让后续剪枝更有效。
  - 内存占用恒定（栈深与分支深度成正比）。最优优先要维护优先队列，队列规模在最坏情况下指数增长——在浏览器里这意味着标签页被杀，而不是「变慢」。
  - 日常算账场景的整数变量通常是个位数规模，两者的求解速度差异不可观测，而内存安全性差异是实打实的。
- **为什么不选其他**：方案 1 在大规模 MILP 上确实更优（探索的节点更少），但那不是本产品的目标规模。
- **后果**：
  - 节点上限 200,000，超出报 `degenerate` 并建议「收紧变量上界或减少整数变量」。
  - 分支时先探 `>= ⌈v⌉` 再探 `<= ⌊v⌋`（栈是后进先出），因为前者更接近原松弛解，更容易快速找到可行整数解。
  - 全精确算术让分支判据没有浮点陷阱：分支界用 `floorDiv` / `ceilDiv`，剪枝比较用有理数精确比较，不存在「0.9999999 被误判为整数」。
- **何时重新审视**：若需要支持上百个整数变量，应同时引入割平面与更优的节点选择策略，而不只是换成最优优先。
